# MV100：Lima 启用、Mesa EGL/GLES 应用与 IRQ 修复

日期：2026-10-29，Asia/Shanghai。此记录接续桌面性能优化，区分早期双PP失败与最终单PP兼容候选。最终上板/持久化结果以本文末尾和交接文档顶部为准。

## 用户态入口

独立 `hi3798mv100-codex-lima.dts` 打开GPU节点；普通 `codex-display` 仍可用于GPU关闭的显示回退。启用Lima后设备分别为：

- `/dev/dri/card0`：simpledrm显示前端。
- `/dev/dri/card1`：Lima渲染GPU，无显示连接器。
- `/dev/dri/renderD128`：普通渲染节点，组为render，未放宽为0666。

ray加入video/render组；新登录或runuser会话继承组权限。Mesa保持系统Debian armhf 22.3.6与libglvnd，不混入SDK softfp库，不全局替换EGL/GLES库。

部署后的最小使用方法：

```sh
mv100-gles2-test                 # 单帧、离屏GLES2绘制与像素校验
mv100-gles2-test /tmp/result.ppm
mv100-mesa-run es2_info.arm-linux-gnueabihf
mv100-mesa-run es2tri.arm-linux-gnueabihf
```

后两个命令在X11桌面终端中执行。`mv100-mesa-run`只给该子进程设置 `MESA_LOADER_DRIVER_OVERRIDE=pl111`，使用系统Mesa已提供的generic kmsro入口；本板没有PL111显示硬件。未显式选择这个入口的X11 EGL客户端曾回落到llvmpipe，不能把GPU节点出现当成所有应用自动加速。

`mesa-utils-bin` 8.5.0-1仅新增约177kB。Debian该包的原生程序名有 `.arm-linux-gnueabihf` 后缀；不能因没有无后缀命令就误判没有安装。

## 实测方法

开发/编译在WSL Ubuntu-24.04/ray，目标运行通过Windows SSH别名hi3798_37_10。候选通过COM8接管fastboot，TFTP约2.7–2.8秒上传约4.9MB，核对SHA256、长度和RAM CRC32后bootm；串口持续采集异常。没有把内核数据经串口慢速上传。

`lima-render-image.c` 动态加载系统libEGL，建立surfaceless GLES2 pbuffer，只画一帧256×256渐变并glReadPixels；要求renderer为Mali/Lima，拒绝llvmpipe。输出EGL/GL版本、vendor、render node、中心RGBA、GL error，并保存PPM。DMA-BUF扩展只记录advertised，不冒充完整导入/导出验收。

完整桌面另用Xorg modesetting/glamor，通过进程级kmsro入口接入Lima。对原生X11 EGL客户端运行包自带es2_info，实际检查GL_VENDOR/GL_RENDERER；再运行包自带es2tri显示有色三角形，并xwd截图。可见窗口与离屏绘制是两条分别验证的路径。

`verify-direct-kms-window.py` 映射/销毁一个96×96红窗口，读取显示桥接物理扫描缓冲首像素，要求出现红色并恢复，避免只用Xorg截图判断实际扫描更新。simpledrm仍要CPU复制变化区域到固定G0缓冲，这不是零拷贝显示驱动。

## 捕获的内核崩溃

第一次双PP候选离屏GLES结果通过，但后续在uptime297秒发生：

```text
Unable to handle kernel NULL pointer dereference ... 0000000c
PC is at lima_pp_bcast_irq_handler+0xa4/0xec
r4=00000002 r0=00000000
Code: ... e7990104 (e590300c)
Kernel panic - not syncing: Fatal exception in interrupt
```

完整证据 `reports/2026-10-29/kernel-next/lima-apps-serial.txt`。随后板子自行回到eMMC保存的GPU关闭内核；本次捕获已经证明这次是内核中断异常，不能只归因为SSH、串口或网络。它不能自动证明此前所有未捕获重启都是同一原因。

对照父提交源码和ARM反汇编：指令从 `pipe->processor[i]` 取ip再读其iomem；i=2已超过本板两个PP，得到NULL。`lima_sched_pipe_task_done()`会发fence，调度器可释放任务/frame，而current_task在正常完成后并未清空；广播处理又在循环条件继续读取frame->num_pp。共享GIC126还使GP/PP各处理函数全部被调用：各PP处理先递减计数，广播处理再次计数，并可能在无有效PP任务时访问旧frame。

本地 `lima_pp.c` 修复：同一IRQ上的独立PP与广播处理只由广播一处计数；task计数≤0时不访问旧任务；缓存num_pp，发完成fence后立即返回；GP与PP共用IRQ时先确认至少一个PP中断确实pending，防止把正在编程但尚未开始的PP当成完成。其他IRQ拓扑保留原行为。

源码参考为本地Linux6.12.114及[上游Lima PP处理](https://raw.githubusercontent.com/torvalds/linux/master/drivers/gpu/drm/lima/lima_pp.c)，没有假定升级最新源码就已经修复本板共享IRQ问题。

## 双PP仍未解决的边界与单PP候选

修复第一版不再出现上述panic，但glamor任务报告 `pp0 job timeout`，PP0已完成、PP1仍被计数，int_state/status均为0。第二版恢复“某PP无中断位但已idle也算完成”的Mali450规则，并只在至少一个PP有真实中断时遍历。原生EGL已能报告Mali450，但双PP仍在部分窗口任务出现相同PP1完成通知超时，因此未把双PP作为最终默认配置。

最终兼容DT仅提供gp/gpmmu/pp0/ppmmu0/pmu/pp六个IRQ名称，省略可选pp1/ppmmu1；Lima只枚举、调度一个PP。芯片仍是Mali450 MP2，**这是明确的单PP兼容模式，不是双核心完整支持，也不能把renderer字符串当成MP2验收**。时钟/电压未调整；先前PMU域0x3修正保留。

候选 `uImage-mv100-lima-single-pp` SHA256 `d84770816886c7c8ae1c6da0c29aa5ca24ff86f110430be375d3580fe39d8cad`。双PP失败镜像和日志分别保留，不能用最终兼容结果覆盖失败记录。

## 实际输出与自动回退

GLES离屏检查在普通ray下得到：

```text
EGL_VENDOR=Mesa Project
EGL_VERSION=1.4
GL_VENDOR=lima
GL_VERSION=OpenGL ES 2.0 Mesa 22.3.6
EGL_DRM_RENDER_NODE=/dev/dri/renderD128
GL_RENDERER=Mali450
GPU single-frame pixel=128,128,64,255 error=0
gles2-exit=0
```

GPU桌面试运行使用180秒timer加持久boot guard；失败/重启时恢复原Xorg/LightDM配置，避免仅放/run的timer因重启丢失。早期几次手工查询/截图超过timer自动退回软件桌面，另一次es2_info在LightDM的Xauthority尚未生成时返回Invalid MIT-MAGIC-COOKIE；这些不冒充GPU应用通过。后续改为单个板端脚本等待会话、检查Mali renderer、捕获es2tri、核对扫描像素与dmesg，无错误才启用glamor profile并取消回退。

通过后的profile按内核/设备选择：现代内核+simpledrm+Lima+glamor-enabled marker时采用glamor；GPU缺失时用已验证的软件modesetting；旧4.4使用原fbdev。Xorg wrapper也检查当前配置才启用kmsro，旧内核直接执行原Xorg。合成器保持关闭，GPU 2D加速不等于必须开启桌面合成。
