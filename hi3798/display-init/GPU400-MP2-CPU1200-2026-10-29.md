# GPU 调频、双 PP 与 CPU 1.2GHz 尝试

日期：2026-10-29，Asia/Shanghai。SDK/源码/构建在WSL Ubuntu-24.04/ray，板端操作使用Windows SSH别名hi3798_37_10并确认hostname/whoami/pwd；异常及TFTP控制经COM8。用户要求日常CPU1.2GHz、GPU调频至400MHz并尝试双PP，沿用单次功能检查、不做长时间压力测试的要求。

## 最终结果与边界

- GPU增加独立CCF频率源 `gpu_dfs`，接入Lima已有的OPP/devfreq；范围200/250/300/345.6/375/400MHz，默认simple_ondemand。明确测试了200→400MHz切换、真实硬件选择器及GLES绘制，不只修改显示数值。
- 双PP候选DRM ABI返回gpu_id=2（Mali450）、num_pp=2；记录两个PP都进入硬件active状态（掩码3），一次1024×1024渐变图、原生es2tri窗口及物理扫描更新通过，没有GPU任务超时/Oops/panic。缺失完成通知使用MV100限定的轮询补偿，**不是宣称已经修好全部硬件IRQ**。
- CPU1.2GHz未通过日常验收。一次短算术比较约1.20倍、校验值相同，随后多核内核异常并自动重启。默认保持1GHz，1200仍隔离为研究用显式cap/overclock入口；1500没有重试。未改变CPU/GPU电压。

## CPU 两次失败的证据

第一候选默认performance开放到1200000kHz，在uptime1.15秒出现PC=0的中断异常，尚未挂载SSD；原始 `daily-clock-onepp-ram-boot.txt`。不能将该候选称为已部署或启动成功。因原panic=0且尚未由systemd启用硬件watchdog，SSH/串口命令无法reboot；用户配合一次断电上电，已提前准备COM8/TFTP修正版。内核分区此时没有写入。

第二候选先以1GHz/userspace正常进入SSD，再在CPU3执行一次24000000轮xorshift计算：

```text
cpu_khz=1000000 seconds=0.149904 checksum=563b371b
cpu_khz=1200000 seconds=0.125108 checksum=563b371b
```

比值1.198，说明当时计算确实加速，不能只因随后失败就抹去这个结果。该测试最后切performance遇到EINVAL，因为诊断默认userspace后performance governor未显式编入；这不是算术校验失败，后续配置已显式包含performance。但在继续GPU测试前，板子已发生多核调度数据异常：CPU3在update_sd_lb_stats读非法地址，其他CPU也报错，uptime100.77秒panic。原始 `daily-runtime-tests-serial.txt`，测试输出 `daily-runtime-function-check.txt`。故短检查不能作为日常稳定性的证明。事先写入运行时panic=5后本次能自动恢复到已保存的旧内核，无需第二次手动断电。

SDK `source/msp/drv/pm/clock_mpu.c:mpu_clk_set_rate()` 的MV100分支明确对QFP216将1200000请求换为1000000，并设置rate_change_flag；FF/SS corner也有同样回退。本板既有硬件采集为QFP216。因此旧4.4显示1200000不足以证明实际长期在1.2GHz工作。当前失败与封装限制/固定电压下超频不稳定相符，但没有独立测得电压或排除所有CPU切频同步因素；不能声称已经证明加多少电压就能解决。

正常源码默认daily_max_khz=1000000；1500继续仅allow_overclock并且userspace显式请求才允许，不会由日常governor自动进入。没有为了满足界面数字而保存会重启的1.2GHz默认值。

## GPU 时钟实现

新增 `drivers/clk/hisilicon/clk-hi3798mv100-gpu.c`，GP/PP门控链的父时钟从固定200m改为gpu_dfs；GPU bus、MMC/SDIO BIU等公共200m均不变。核心时钟以CRG0x154 bit[7:5]回读实际选择状态，set_rate按SDK流程配置GPU专用PMC0xb0/0x48/0x54与CRG0x124选择、趋势和请求握手。选择已有PLL输出档位，不重编PLL、不写电压。

只开放200–400MHz设置；读取函数可解释SDK全部8个硬件选择值，避免把未支持的boot值读错。转换有20ms硬件状态确认，失败恢复原GPU专用寄存器并报错，不把未落地的频率报成成功。没有把共享200m改成400m。

在Lima DT加入operating-points-v2，沿用上游lima_devfreq.c，与performance/userspace/simple_ondemand governor配合。框架依据：[CCF](https://docs.kernel.org/driver-api/clk.html)、[OPP](https://docs.kernel.org/power/opp.html)。CONFIG_DEVFREQ_GOV_PERFORMANCE/USERSPACE均内建；正常CPU governor恢复performance。

1PP和2PP分别检查均得到：GPU cur_freq先200000000再400000000，Mesa22.3.6 / EGL1.4 / GLES2 / renderer=Mali450，中心像素128,128,64,255，GL error=0。GPU400时只读状态：

```text
CRG48=00000700 CRGd4=00000701 CRG124=00000001 CRG154=05561131
```

GPU请求/实际选择均1，即SDK标称400MHz；CPU实际选择仍0，即标称1GHz。工作后恢复simple_ondemand，观察到空闲cur_freq回200MHz，上限400MHz。没有把空闲降频误判为提频失败。

可读取 `/sys/class/devfreq/f9200000.gpu/{available_frequencies,governor,cur_freq,min_freq,max_freq}`；需要固定400MHz时可将governor设performance。中间档位来自SDK表，尚未逐档做图形验收。当前共享CPU/core电源未通过独立regulator控制，OPP注册会记录无mali regulator及未注册cooling设备的信息；实际devfreq和调频可用，不将这些可选项日志当成GPU未注册。

## 双PP完成通知兼容

保留原先的共享IRQ去重、无活动任务不访问旧frame、完成fence后立即返回。新增仅针对MV100且num_processor>1的工作：

1. PP提交、广播IRQ与轮询使用同一spinlock，避免重复完成或同时释放任务。
2. 只有实际发出PP启动命令后才设置started；无中断时允许读取各PP的active状态并完成已经idle的PP。
3. delayed_work仅在任务活动时检查，最多1秒；随后仍由正常GPU scheduler报告真卡死，不用无限轮询掩盖故障。
4. 完成、错误及退出取消轮询；暴露只读 `mv100_pp_poll_jobs` 与 `mv100_pp_seen_active`，使兼容路径可审计。

当前HZ=100，msecs_to_jiffies(1)实际最小约10ms，所以这是有潜在延迟开销的完成补偿，不能据双PP枚举就声称桌面必然翻倍。没有做长期GPU压力或帧率基准。

DRM ABI通过ARM标准ioctl读取NUM_PP，不仅看renderer名字；测试结束轮询完成任务数1、active掩码3，随后正常桌面计数增至5，内核仍无任务超时。1024×1024图中心127,127,64,255，符合低精度渐变容差；截图 `es2tri-gpu400-mp2.png` 已人工查看。图形buffer的CPU呈现仍经simpledrm，不宣称新增原生G0零拷贝驱动。合成器/XPresent沿用用户确认的设置，没有再次关闭。
