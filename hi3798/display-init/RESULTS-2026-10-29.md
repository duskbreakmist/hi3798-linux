# Linux 6.12：显示、USB 输入及 Mali 实验记录

记录日期：2026-10-29，Asia/Shanghai。本轮从 2026-10-28 延续，原始日志仍集中在 `reports/2026-10-28/kernel-next/`。板上时钟曾与开发机不一致，不能按串口内核 uptime 或板上文件日期推断跨次启动的真实时间。

## 结论与验证边界

1. HDMI 1080p60、G0 图形扫描、主线 simpledrm、`/dev/fb0`、LXQt 桌面已接通。用户确认桌面正常、显示范围正常。
2. 初始化已内建为 `CONFIG_HI3798MV100_DISPLAY_INIT=y`，正常重启可自动从 SSD 进入桌面，不再依赖手工 insmod。该阶段已刷入 eMMC 并回读验证。
3. USB Hub 后全速键鼠的 `EBUSY` 已定位到 EHCI TT 调度配置遗漏；启用 `CONFIG_USB_EHCI_TT_NEWSCHED=y` 后 Xorg 成功打开 Logitech 鼠标和 CHERRY 键盘的全部相应输入端点。记录时仍需区分日志接入成功与用户实际移动、键入的确认。
4. Mali/Lima 新候选在 RAM 引导下通过一次 256×256 GLES2 渐变图绘制和完整读回。Mesa 为 armhf 22.3.6，renderer 为 `Mali450`，中心像素 `(128,128,64,255)`；GPU IRQ 计数由 0 变为 2。任务结束后重新进入 runtime suspend，未记录 GPU fault/timeout。
5. GPU 验证只覆盖这一帧与这次电源状态转换；没有重复绘制压力测试，不能据此宣称所有历史卡死问题已解决。当前 Xorg 使用 fbdev、xfwm4 会话；未验证整个桌面合成器、浏览器或视频解码使用 GPU。

## 研究方法

按硬件输出、内核设备、用户态会话、GPU 渲染分别取证。编译成功、设备节点存在、renderer 字符串、IRQ 增加都只是链路中的证据，不能单独替代画面或像素验证。

开发和 SDK 读取在 WSL Ubuntu-24.04/ray 执行，实际运行通过 Windows SSH 别名 `hi3798_37_10`，异常启动通过 COM8 接管。新候选通过 fastboot TFTP 加入 RAM，传输约 2.7–3.7 秒；逐次核对 SHA256、传输长度、RAM CRC32，再 bootm。未通过的候选不刷写，不改持久 bootcmd/environment。

显示初期使用 RAM initramfs，磁盘分区不挂载。`display` 命令先启动 20 秒 SP805 看门狗，再加载实验桥接；`reboot` 命令可自行回到 fastboot。每次修改解决一个实际失败点，没有对已通过的渲染流程做自主循环压力测试。

## 显示链路的关键发现与修正

### 1. simpledrm 缺少可接管的显示状态

根据本芯片 SDK `hi_reg_vdp.h` 用 `offsetof` 编译取得 G0 偏移：CTRL=0x6000、ADDR=0x6010、STRIDE=0x601c、IRESO=0x6020、DFPOS/DLPOS=0x6080/0x6084。VDP 基址是 0xf8cc0000。

fastboot 只读结果为 CTRL=0x40000000（surface_en=0），地址、步长、尺寸均为 0。由此确认没有现成 framebuffer 可交接，直接启用 simpledrm 无法让本板输出桌面。证据 `perf-final-boot-2.txt`，工具 `vdp-register-offsets.py`、`fastboot_net_boot.py --inspect-display`。

### 2. 提取精简初始化，保留现代显示前端

选择 SDK boot 路径中的 12 个 VDP 源码单元和 13 个 HDMI 1.4 源码单元，均使用 MV100/3798m 分支。在独立输出目录复制、修改及编译，原 SDK 未修改。

移植文件在 `/home/ray/workplace/hi3798-linux-build/display-init-port/`，构建入口 `scripts/kernel-next/build-display-init-port.py`。替换 bootloader 依赖为小型声明头、Linux 日志与延时，将 VDP/HDMI 常用 MMIO 访问转换为 ioremap 后的虚拟地址。通过 modpost 检查剩余符号，修复旧代码与内核 wchar_t 大小不一致的问题。

没有把 softfp SDK 用户库装入 armhf Mesa 进程，也没有全局更换 EGL/Mesa 库。初始化代码仍来自 SDK，原许可保留；这不是声称主线已有 MV100 HDMI 驱动。现代显示前端是 Linux 自带 simpledrm，GPU 内核驱动是 Linux 自带 Lima。SDK 原源码/二进制库未被添加到本项目 Git；内核构建时从本地 SDK 源码生成初始化目标文件。

### 3. HDMI 初始化顺序

首版 VDP 初始化成功，但日志 `HI_UNF_HDMI_Open Err`、Rsen=0。SDK 的 `HI_DRV_HDMI_Init()` 是轻量封装，不能替代 `HI_UNF_HDMI_Init()` 的 HW_ResetHDMITX、软件复位与 PHY 操作。

对照 SDK `source/boot/product/main.c` 的 Logo 流程，补上独立 `HI_UNF_HDMI_Init()`，延时后以 1080p60 打开 HDMI，得到用户确认的蓝屏。证据 `display-init-ram.txt`（失败环节）、`display-init-ram-2.txt`（明确 HDMI init/open 返回0）。外层函数返回0不代表内部 HDMI 已成功，必须检查子步骤日志。

### 4. 图形层与内存

新增显示专用 DT，预留 `0x3e000000..0x3e7fffff` 共8 MiB，`no-map`；chosen 中声明 1920×1080、stride7680、XRGB8888 的 simple-framebuffer。CMA 自动移动到0x3c000000，未与显示缓冲重叠。物理内存仍1 GiB，Linux 可用内存约993 MiB。

利用 SDK VDP 的 G0/GP0 寄存器函数配置地址、分辨率、全局透明度、禁用压缩/缩放、RGB→BT709 CSC、混合层优先级及寄存器更新。MV100 G0 的 stride 寄存器按16字节计，因此7680字节应写480，而非7680。该规则由本芯片 HIFB HAL 的 `surface_stride = u32Stride / STRIDE_ALIGN`（STRIDE_ALIGN=16）交叉确认。

首次 simpledrm 已打印内核 fb0，但 `/dev/fb0` 不存在，定位到 `CONFIG_FB_DEVICE` 未启用；新增 y 后用户态可访问。彩条通过 fbdev 写入，另有显式开启的直接扫描缓冲写入，仅用于区分刷新和硬件扫描问题，不用于正常启动。

调试中首像素回读0曾被怀疑为未刷新。随后用户确认彩条和闪烁光标，证明不能以单个角落像素推断整帧是否刷新；fbcon 光标/背景会改写该位置。切换到正常 SSD 桌面后用户确认整个显示范围正常，无需把最初彩条范围的描述当作持续故障。

### 5. 内建集成与旧服务

内建驱动位于 `drivers/gpu/drm/tiny/hi3798mv100-init/`，只有匹配 MV100 且 DT 提供准确的预留缓冲时才初始化。普通非显示 DT 跳过硬件操作。构建脚本会生成 codex、codex-io、codex-display；GPU 试验另使用 codex-lima。

在 SSD rootfs 为 `load-kmod.service`、`hifb-1080p.service`、`hifb-display-guard.service` 添加 `ConditionKernelVersion=<5.0` drop-in，避免4.4私有模块/守护程序与6.12新显示流程交叉运行；保留4.4恢复启动的原入口。

## USB 输入故障

现象：USB 枚举和 `/dev/input/event*` 均存在，桌面显示正常，但部分键鼠端点无法由 Xorg 打开，日志 `Device or resource busy`。

源码 `drivers/hid/usbhid/hid-core.c:usbhid_open()` 表明，周期URB带宽不足 `-ENOSPC` 会转成 `-EBUSY`。拓扑 `lsusb -t` 显示多只12Mbps HID 位于480Mbps Hub之后，而当前 allnoconfig 迁移未启用 `USB_EHCI_TT_NEWSCHED`。该 Kconfig 的说明明确针对多只低/全速周期设备位于高速Hub后的带宽调度。

增加配置后，Xorg 将鼠标/键盘各相应端点成功加入 XINPUT，不再报该错误。证据 `display-builtin-ram.txt`、`display-persistent-state.txt` 及后续 Xorg采集。没有通过放宽全局设备权限解决这个问题。

## Mali PMU 兼容研究

### 依据

- SDK 4.4 `arch/arm/boot/dts/hi3798mv100.dts` 与 Utgard `platform/mali450/mali4xx.c` 都为 MV100 提供 PMU 映射 `{1,2,2,...,1,2,0}`：GP/L2_0 为bit0，两个PP及其L2共享bit1。
- `common/mali_pm.c` 使用该配置覆盖通用硬件默认映射。
- Linux6.12 `drivers/gpu/drm/lima/lima_pmu.c:lima_pmu_get_ip_mask()` 的通用Mali450路径对PP0使用bit1，对PP1–3使用bit2。因此带两个PP的MV100会按通用路径构造0x7，而本板域映射应为0x3。

### 改动与假设边界

仅对 `hisilicon,hi3798mv100-mali` compatible 返回 `BIT(0)|BIT(1)`；其他Mali平台不变。初始 power-up 仍使用硬件状态寄存器，power-down 使用本板正确域mask。

这一差异是明确的硬件兼容问题，也可能与此前重复绘制后的卡死有关。但旧日志没有完整记录卡死瞬间，因此不能把“已发现差异”升级为“已证明所有卡死都由它导致”。

当前 GPU 门控继续沿用 SDK 的CRG53 bit0/8/9/10及bit4 reset；未修改PLL或GPU电压。时钟树的200MHz仍是早先占位模型，不能当作独立测得的GPU频率。SDK MV100选择器表包含432/400/375/345.6/300/250/200/500MHz；完善真实时钟模型属于后续工作。

### 单帧验证

镜像 `uImage-mv100-lima-pmu` SHA256 `ddea1c7b41a633330a6968f39b40e0ef279357edd6a5dc7a06225dd09bb2efe8`，与正常显示镜像分开保存。

`lima-render-image.c` 通过现有 armhf Mesa EGL 创建 surfaceless GLES2 pbuffer，检查 renderer 必须为Mali/Lima且非llvmpipe。只执行一次256×256三角形绘制，fragment shader输出位置渐变，然后 glReadPixels 完整读回并检查中心像素，输出PPM。没有循环压力绘制，没有更换系统图形库。

结果：EGL1.4，renderer=Mali450，中心RGBA=128,128,64,255，GL error=0，进程exit0。IRQ从0增为2；测试前runtime_status=suspended，提交结束时active，随后再次suspended，系统SSH仍可用，日志无GPU fault/timeout。

证据：`lima-pmu-before.txt`、`lima-pmu-single-frame.txt`、`lima-pmu-after.txt`、`lima-render.ppm`、`lima-render.png`。图像导出的RGB范围R/G=0..255、B=63..64，与shader和低精度量化吻合。

## 自行截图方法

先通过 Xorg `xwd -root` 保存X窗口截图，再使用内核FBIOGET_VSCREENINFO/FBIOGET_FSCREENINFO取得实际1920×1080、32bpp、stride7680，读取 `/dev/fb0` 并转换为PNG。simpledrm 的 fbdev 前端可以是 shmem 影子缓冲（本次 smem_start=0），因此截图证明的是该前端当前绘制内容，不能单凭PNG证明HDMI电信号已经正确输出。本轮同时结合了用户对彩条、桌面和显示范围的现场确认，以及G0扫描配置，作出显示链路通过的判断。

`capture-framebuffer.py` 在板上执行，`.json` 保存实际布局，Windows Pillow按BGRX转换。`desktop-gpu-proof-full.png` 展示桌面及单帧验证结果窗口；该窗口显示的是采集结果摘要，不是宣称窗口本身由GPU合成。真正GPU产出的图像为 `lima-render.png`。

原有 LXQt 面板为自动隐藏，截图只见壁纸/窗口不代表面板未启动。lximage-qt 进程曾立即退出，未将其当作GPU或显示失败证据；验证结果窗口改用Xlib的xmessage。

## 本轮结束状态

持久化内核是已确认的显示/TT调度基线，GPU节点默认关闭；当前RAM运行的是含PMU修正的GPU试验候选，renderD128可用，单帧结果已保存。没有把仅通过单帧检查的GPU试验默认覆盖已验证显示基线；普通重启会回到持久化桌面内核。研究补丁和GPU专用镜像均保留，可重复构建/继续迭代。

收尾源码另修正了 HDMI 初始化失败后的资源清理：关闭已打开的显示通道、清除 opened/gfx_active 状态并清空已 iounmap 的指针，避免后续状态查询访问失效映射。该失败分支仅完成编译检查，没有额外做拔插测试。诊断 initramfs 同时支持检测已内建的显示初始化、检查看门狗关闭返回值，静态交叉编译无警告。
